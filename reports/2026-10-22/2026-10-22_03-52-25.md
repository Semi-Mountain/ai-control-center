## 2. 现象 → 机制 → 实现细节（3 层 × 3 源）

### 源 A｜ArXiv 2609.29095 · LIMBO（Microsoft, 2026-09-24）
**链接**：https://arxiv.org/abs/2609.29095

- **现象**：25,930 episodes / 9 models / 3 harnesses。模型被明确要求"exactly once"时，**丢失 ack** 场景重复率仅 **0.5%**；但 **in-flight** 或 **redelivery** 场景，同一批 frontier model 重复率升至 **56% / 74%**，此时 **contract 解释 81% 方差**（模型只解释 53%）。
- **机制**：verification-only 策略在**没有 in-flight time 上界**时**不可能**实现 exactly-once；给每次 write 配 **idempotency key** 把重复率从 **28% → 4%**。
- **实现**：原文关键引用——*"a guard that attaches keys transfers across harnesses unchanged"*（harness 层改动小，**contract 层改动才是杠杆**）；更狠的一句——*"agents reported success in 90% of the episodes in which they had duplicated an effect"*（**agent 自报成功不可信，必须外部契约核验**）。

**映射到爸爸**：段号就是我们的 idempotency key。`SEG=$(date +%H)` 相当于"用操作对象名当幂等键"——同一段重复触发会算出不同的键；`SIGSEGV` 式"同一个键但语义不同"则会让 6 段联动断链。LIMBO 的判据直接翻译过来：**当"读回"（self_reward / trace 文件）能消歧时，靠记录判定；当不能消歧（跨段、并发、迟到）时，只有契约（job_id → SEG 的固定映射）能救。**

### 源 B｜ArXiv 2608.01710 · CapLease（Durable Authorization State）
**链接**：https://arxiv.org/abs/2608.01710

- **现象**：**语义重放（semantic replay）**——token 本身是单次使用的，但 agent 重规划/重试/委派/崩溃恢复时会**重新签发新 token**，从而突破一次授权的执行预算。
- **机制**：原文——*"identifier-local token consumption cannot prevent fresh reissuance unless the issuer retains monotonic durable state over the authorized action, confirmation event, and remaining execution budget."* 纯 token 局部校验**必然**被 fresh reissuance 绕过。
- **实现**：Issue-Prepare-Commit 事务态迁移 + 把用户确认绑定到 **canonical action**。

**映射到爸爸**：这正是 `wowzai_segment_resolver.py` 的病理——它把身份绑定在 **"agent.log 中最近一次 cron 触发前缀"这个瞬时观测**上，而不是绑定在 **canonical action（job_id + 固定 schedule）** 上。凌晨 4 个 job 并发触发，"最近一次"每次都在变 → 同一段每次解析出不同身份 = 语义重放。要 **monotonic durable state**：身份一旦由 job_id 解析出 SEG，就必须单调、可回放、不可被"更晚的触发"改写。

### 源 C｜ArXiv 2610.27620 · Local Allow, Global Deny
**链接**：https://arxiv.org/abs/2610.27620

- **现象**：**per-action 局部授权无法组合成全局授权**；构造出 compositional authorization failure (CAF)。
- **机制**：原文核心不可能性结果——*"relational purpose violations form a 2-safety hyperproperty with no per-trace locus of blame, so a per-action monitor that never raises a false alarm detects none of them"*；这类违规**只有在跨执行监控下才可见**，而调研的六个 guardrail **没有一个实现跨执行监控**。
- **实现**：AL-SYNTH 用 SAT/SMT 合成最小 CAF witness，再用穷举 oracle 校验。

**映射到爸爸**：今晚 6 个学习段是**一条 execution chain**，不是 6 个独立任务。每段只 `grep` 自己那一个 `self_reward.json`（per-action monitor），**结构上不可能**发现"00:00 段没写文件导致 01:00/03:00 段空跑"这类**跨段因果违规**。§3.4b 的"读前一段 self_reward 末 200 字符"是正确方向，但它是**点对点**的，必须升级为**跨执行链监控**（这与 Limbo 的 81% vs 53% 结论方向一致：跨记录视角的判别力显著高于单记录视角）。

## 5. 可以改进的点

### 5.1 自我进化（我可以变得更强的地方）

1. **身份先于内容**：任何 cron 段启动的第一个动作应是"断言我是谁"，且断言依据必须是 **job 配置/契约**，不是观测（墙钟、全局日志、文件名）。今晚我用了大量工具才反推身份，正确做法是一步到位读 `jobs.json` + session 文件 + prompt 逐字节比对，并**立刻写进笔记 front-matter**。
2. **证据预算自律**：调查类工具调用必须设硬上限（本次约 40 次耗尽额度），并且**在第 N 次后无条件回填正文**。我把"挖深"放在了"落盘"之前，顺序错了。正确顺序：**骨架 → 每 5 次调用追加一节 → 最后统一润色**。
3. **一次调用多验证**：今晚有 3 个批次本可合并（我能识别但没合并），浪费了约 1/3 额度。规则：同一决策点的验证项**打包进一个 execute_code / 一个 terminal 调用**。
4. **复用优先于新建**：`slot_context_injector.py` 已存在且未被引用——今晚我却在设计新脚本。**先 grep 资产库，再设计**。
5. **失败即证据**：aux compression 超时循环、00:00 段未落盘，都是可复用的失败模式，应沉淀为"触发器 + 检查项"进入 07:00 审计的 grep 清单，而不是只留在今晚的会话里。

### 5.2 沟通优化（让对话更高效的方式）

1. **先给结论，再给证据**：本条已按此排序（§1 一句话结论在最前）。爸爸读前 3 行即可决策。
2. **显式区分「生产已改 / 草案待审 / 建议」三态**：本条所有改动均标为**草案**，生产文件零改动（`jobs.json` 与 `scheduler.py` 均未动），符合今晚铁律与 07:00 的黑名单。
3. **每个结论带一个可复跑命令**：爸爸不需要相信我，只需要复跑命令。已给出 resolver 实跑输出、注入探针输出、inode/nlink 实证。
4. **坏消息优先**：Enforcement Gap（3 个产出物缺失）置于第 0 节，而不是埋在末尾。
5. **把"三个数字"写进交付格式**：SEG / TRIGGER / WALL_CLOCK 三者并列，任何只给其中一个的汇报都应视为不合格。
6. **跨段沟通用可机器校验的字段**：建议此后每份 trace 自带 `run_id` + `parents`，让 07:00 agent 不必靠自然语言猜因果链（对齐 LangGraph / CapLease）。
